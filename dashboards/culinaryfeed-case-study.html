Engineering + product case study

CulinaryFeed is a TikTok-style recipe discovery app with a full recommendation engine — multi-dimensional affinity, a bandit for exploration, diversity-constrained ranking — running entirely in the browser, with no backend and no real users yet. Here's how it's built, and how I proved it works anyway.

01 / The setup

No backend. No users. Just a claim to prove.

The brief I gave myself: build the recommendation layer a real food-discovery product would need — the part that decides what you see next — and prove it actually personalizes, before a single real person opens the app.

Everything lives in the browser. Every swipe, save, rating, and dismissal becomes a telemetry event, buffered to localStorage and reduced into session facts on the client. There's no server to hide behind — if the ranking looks wrong, it's because the logic is wrong, not because a query timed out somewhere.

"If it can't prove itself against synthetic data, it has no business ranking real people's dinner."
02 / How a recommendation happens

Five stages, zero round-trips.

01

Feed & actions

Swipes, likes, saves, dismissals, ratings, follows, and full cook sessions with a step timer.

02

Telemetry buffer

Every action becomes a typed event envelope, persisted to localStorage the moment it fires.

03

Session transform

Raw events reduce into per-recipe impression facts — dwell time, expand rate, ingredient completion.

04

Affinity model

Recency-decayed weights across four dimensions at once: cuisine, difficulty, diet, and content tags.

05

Ranking engine

Scores every unseen recipe, explores under-shown cuisines via UCB1, then diversifies the final order.

03 / The ranking algorithm

Six ideas doing the actual work.

Each one exists to fix a specific, observable failure mode of a naive "rank by cuisine affinity" feed.

Signal shape

Multi-dimensional affinity

Weighs cuisine, difficulty, diet, and content tags as four parallel vectors instead of one — a vegan user gets credit for being vegan, not just for whichever cuisine they happened to click.

Time

Recency-weighted scoring

A 14-day exponential half-life on every signal, so taste is allowed to drift instead of averaging a person's entire history into mush.

Variety

Diversity constraint

Caps any one cuisine at 2 appearances per 5-card window — even for a user whose affinity vector is 91% one cuisine.

Discovery

Content-based similarity

Weighted Jaccard similarity over ingredients and tags powers "More Like This" — connections cuisine-only affinity can't make.

Exploration

UCB1 bandit

Replaces a flat epsilon-greedy random chance with an exploration bonus that shrinks as confidence in a user's taste grows.

Feedback

Explicit negative signal

A real "not interested" action carries a −6.0 penalty — the single largest-magnitude term in the whole scoring function.

05 / What actually got verified

Claims are cheap. Here's what I checked.

No test runner was available in the build environment, so every claim below was checked by actually executing the real ranking code against real persona data — not by trusting the design doc.

✓

A user whose taste visibly drifted — North Indian, then Korean, then French, across three sessions — ended up with a french: 0.844 affinity weight. Recency decay works: the most recent session dominates instead of averaging out.

✓

A user with a italian: 0.91 affinity skew — about as extreme as it gets — still never saw more than 2 of 5 consecutive cards from the same cuisine. The diversity constraint holds even at the edge.

✓

A brand-new onboarding profile (Thai + Mexican preference, beginner, vegan) produced an exact 70/30 preference-weighted split across cuisine, difficulty, and dietary dimensions simultaneously — cold start isn't a coin flip.

✓

Dismissing a recipe removes it from the ranked output permanently — verified by re-running the ranking engine with the dismissal applied and confirming the recipe never resurfaces.

06 / How it's built

Deliberately no backend.

Every piece of state — saved recipes, ratings, dismissals, follows, the meal planner, the shopping list — is a small, dependency-free localStorage-backed service. When the build environment had no network access to install a bundler, I verified the ranking and affinity modules by directly executing them under Node with a minimal browser-global polyfill, rather than skipping verification entirely.

07 / What's still open

This isn't finished — on purpose.

01

Explainability — a "because you liked Thai food" chip on each card. Last piece of the product-polish pass.

02

Live re-ranking — right now a session's feed is ranked once on mount; it should react mid-session.

03

An A/B harness — to run two ranking strategies side by side against the same synthetic personas.

04

Real automated tests — the verification above was direct execution + hand-written assertions; it deserves a real suite.
