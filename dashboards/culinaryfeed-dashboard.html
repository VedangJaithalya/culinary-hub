01: Product

What CulinaryHub is, and how it's built

A vertical, swipe-through recipe discovery feed (the TikTok-for-recipes format) with a fully client-side recommendation engine. There is no server: every preference, rating, save, and event lives in the browser's own storage, and a ranking pass reruns from that history alone.

How a recommendation actually gets made

Five stages, entirely client-side: no request ever leaves the browser.

01 Feed & actions Swipes, likes, saves, dismisses, ratings, cook sessions.
→
02 Telemetry buffer Every action becomes an event, buffered to localStorage.
→
03 Session transform Raw events reduce to per-recipe impression facts.
→
04 Affinity model Recency-decayed weights across cuisine, difficulty, diet, tags.
→
05 Ranking engine Scores, explores via UCB1, and diversifies the feed.

02: Users

The user base is 20 synthetic personas

There's no production traffic yet. What stands in for a user base is a deliberately hand-built cast of 20 personas, one dataset per behavioral edge case the ranking engine needs to survive, from a single-cuisine loyalist to pure adversarial noise. Every affinity and diversity claim on this dashboard is tested against them.

Coverage gap

◆
9 of the 14 defined event types have zero synthetic coverage: ratings, follows, dismissals, cook-mode starts/completions, onboarding completion, ingredient-list adds, and shares. All were added to the schema and shipped in the app after these 20 fixtures were generated. The ranking engine's negative-feedback and rating logic is verified by direct execution against hand-written test cases, not by any persona's simulated history.
